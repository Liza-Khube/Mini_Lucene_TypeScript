# Mini Lucene (TypeScript)

## **Огляд проєкта**

**Тема проєкту: Повнотекстовий пошуковий рушій**

**Опис проєкту:** Система є спрощеним аналогом Lucene - пошукового рушія. Рушій приймає колекцію текстових документів, будує над ними позиційний інвертований індекс, і дозволяє виконувати над цим індексом булеві та фразові запити з ранжуванням результатів за релевантністю (BM25).

Усе ядро - токенізація, стемінг, індекс, стиснення, парсер запитів, ранжування, нечіткий пошук - реалізується самостійно, без сторонніх бібліотек. Сторонні бібліотеки допустимі лише для інфраструктури розробки (тест-раннер, fast-check, Stryker), а не для самого алгоритмічного ядра.

Робота з системою відбувається через інтерактивну консольну сесію (REPL): користувач один раз запускає CLI, індексує колекцію документів, а потім вводить довільну кількість пошукових запитів у межах одного процесу.

**Мова реалізації:** TypeScript.

## **Архітектура та структура модулів**

### **Модулі:**

**1) Аналізатор тексту (Text Analyzer):** Обробляє вхідний текст: токенізація, нормалізація регістру (нижній регістр), фільтрація стоп-слів, алгоритм стемінгу (Porter stemmer);

**2) Позиційний інвертований індекс (Inverted Index):** Основна структура даних у пам'яті, яка формує словник термінів та зберігає ідентифікатори документів разом із масивами точних позицій входження кожного слова;

**3) Стиснення та серіалізація (Compression & Serialization):** Відповідає за компактне представлення числових послідовностей у типізованих масивах Uint8Array. Використовує алгоритми delta-encoding для збереження різниць між числами та Variable Byte Encoding (varint) для зменшення байтового об'єму чисел; та зберігає й читає весь індекс як один бінарний файл.

**4) Парсер запитів (Query Parser):** Аналізує запит методом рекурсивного спуску для побудови AST запитів з операторами AND, OR, NOT, дужками та лапками.

**5) Виконавець запитів (Query Executor):** Обходить дерево і повертає множину номерів документів, що відповідають запиту.

**6) Модуль ранжування (Scoring & Ranking):** Оцінює релевантність знайдених документів за математичною моделлю BM25 та відбирає найкращі результати (Top-K)

**7) Модуль нечіткого пошуку (Fuzzy search):** Виконує пошук схожих слів у збереженому словнику на основі розрахунку відстані Левенштейна, якщо термін позначено ~ і його немає в словнику, він замінюється на схожі терміни на відстані не більше 2. Пошук реалізується класичним алгоритмом динамічного програмування для відстані Левенштейна з повним перебором словника, без додаткових структур (автоматів, префіксних дерев). Позначка ~ застосовується лише до одиночного терміна, а максимальна відстань фіксована і дорівнює 2.

**8) Оркестратор (SearchEngine)** : Є єдиною точкою входу, яка приховує внутрішню структуру шарів від CLI та оркеструє іншими шарами.

**9) Консольний клієнт (CLI, REPL)**

### **Схема шарів системи:**

Система побудована у вигляді шарів:

| Шар                | Модулі                         | Залежить від                 |
| ------------------ | ------------------------------ | ---------------------------- |
| 1. Presentation    | CLI, REPL                      | Application                  |
| 2. Application     | SearchEngine (оркестратор)     | Domain, Data, Infrastructure |
| 3. Domain (логіка) | Query Executor, Ranking, Fuzzy | Data (Index)                 |
|                    | Text Analyzer, Query Parser    |                              |
| 4. Data            | Inverted Index                 |                              |
| 5. Infrastructure  | Serialization & Compression    | Data (Index)                 |

## Вхідні дані та модель документа

Система приймає колекцію текстових файлів у форматі **.txt** із кодуванням UTF-8. Інші формати не підтримуються, під час індексації вони пропускаються з попередженням у консолі.

Один .txt-файл є одним документом колекції:

● **source** - шлях до файлу, указаний під час індексації - зовнішній ідентифікатор документа: відображається у результатах пошуку в CLI, використовується для перевірки унікальності під час індексації, не індексується і не впливає на ранжування

● **rawText** - повний вміст файлу - передається в Text Analyzer, токенізується й індексується, на ньому будується позиційний індекс і рахується довжина документа для BM25

## **Технічні рішення**

**Мова колекції та токенізація.** Система розрахована на англомовні тексти, оскільки Porter stemmer працює лише з англійською мовою. Токеном є максимальна послідовність символів a-z та цифр 0-9 після переведення тексту до нижнього регістру; усі інші символи (пробіли, розділові знаки, літери інших алфавітів, емодзі) є роздільниками. Те саме правило застосовується до тексту документів і до термінів запиту.

**Стоп-слова.** Для фільтрації тексту використано базовий набір стоп-слів для англійської мови, що базується на [еталонному списку проєкту Apache Lucene](https://github.com/apache/lucene/blob/main/lucene/analysis/common/src/java/org/apache/lucene/analysis/en/EnglishAnalyzer.java): "a", "an", "and", "are", "as", "at", "be", "but", "by", "for", "if", "in", "into", "is", "it", "no", "not", "of", "on", "or", "such", "that", "the", "their", "then", "there", "these", "they", "this", "to", "was", "will", "with".

**Ідентифікатори документів і позиції.** Внутрішній ідентифікатор документа (DocId) - послідовне ціле число, що починається з 0 і присвоюється індексом під час додавання документа. Файли перед індексацією сортуються за шляхом, тому для однієї колекції DocId завжди однакові. Саме DocId зберігається в постингах і стискається delta-кодуванням, а шлях до файлу (source) є зовнішнім ідентифікатором. Таблиця «DocId - source, довжина документа» входить до складу індексу й серіалізується разом із ним. Довжина документа - кількість проіндексованих токенів (без стоп-слів).

Позиція слова - порядковий номер слова в тексті, що починається з 1. Стоп-слова не потрапляють в індекс, але займають позицію, тому позиція збігається з номером слова у файлі.

**Граматика запитів.** Парсер підтримує такі правила:

● пріоритет операторів: NOT вищий за AND, AND вищий за OR; дужки змінюють порядок обчислення;

● оператори AND, OR, NOT розпізнаються лише великими літерами; слова and, or, not в нижньому регістрі є звичайними словами запиту і, будучи стоп-словами, відкидаються;

● кілька термінів підряд без оператора означають AND: people soup еквівалентно people AND soup;

● фраза - слова в подвійних лапках: "brown pillow";

● нечіткий пошук позначається символом ~ одразу після окремого терміна (catt~); до фраз ~ не застосовується, максимальна відстань фіксована і дорівнює 2;

● глибина вкладеності дужок обмежена (50 рівнів), її перевищення дає ParseError.

## **Стратегія тестування**

Тестування побудовано за принципом піраміди: найбільше швидких ізольованих unit-тестів, над ними property-based тести для інваріантів, потім невелика кількість наскрізних (e2e) сценаріїв, а також golden-тест для stemmer і мутаційне тестування для оцінки якості самих тестів.

### **Unit-тести**

Кожен модуль перевіряється ізольовано, без залежностей від інших шарів.  Базове покриття і швидка діагностика.

### **Property-based тести (fast-check)**

Виконується за допомогою бібліотеки fast-check. Замість перевірки окремих заздалегідь підготовлених значень тест формулює загальну властивість, яка має виконуватися для будь-яких вхідних даних. fast-check генерує сотні випадкових входів.

Сценарії за модулями:

● **Text Analyzer.** Для випадкових текстів із літер, цифр і розділових знаків токени завжди непорожні, у нижньому регістрі й не містять роздільників, а позиції токенів строго зростають. Токенізація та нормалізація регістру ідемпотентні: повторне застосування до результату, з'єднаного назад у рядок, нічого не змінює. Для стемінгу ідемпотентність не перевіряється, бо алгоритм Портера її не гарантує, натомість перевіряється, що він детермінований і ніколи не подовжує слово. На екстремальних рядках (емодзі, ієрогліфи, керівні символи Unicode, довгі послідовності пробілів) аналізатор не кидає винятків і повертає валідний (можливо порожній) масив токенів.

● **Inverted Index.** Для випадкової колекції сума частот терміна за всіма документами дорівнює кількості його входжень у вхідних токенах, документна частота терміна (df) дорівнює кількості документів із цим терміном, постинги впорядковані за ідентифікатором документа, а позиції в межах документа строго зростають.

● **Query Parser.** Для випадкових послідовностей термінів, AND, OR, NOT, дужок, лапок і ~ (зокрема з незбалансованими дужками й ізольованими операторами) парсер повертає AST або кидає лише власну помилку ParseError, без зависань та інших винятків; глибина вкладеності обмежена, щоб уникнути переповнення стеку.

● **Query Executor.** Для випадкових підзапитів A і B виконуються співвідношення A AND B ⊆ A, A ⊆ A OR B, AND та OR комутативні. Окремо перевіряється відповідність еталонній моделі: результат SearchEngine для випадкового запиту порівнюється з результатом простої еталонної реалізації, яка не використовує індекс, а для кожного документа окремо перевіряє, чи задовольняють його токени запит. Множини знайдених документів мають збігатися.

● **Scoring & Ranking.** Для довільних індексів із випадковими довжинами документів і частотами термінів BM25-оцінка завжди скінченна, не NaN і невід'ємна. Для двох документів однакової довжини, де термін зустрічається N та N+1 разів, оцінка другого строго більша. Результат упорядкований за спаданням, а Top-K є префіксом повного ранжування довжиною min(K, n).

● **Compression & Serialization (після MVP).** Для довільних зростаючих масивів документів виконується decode(encode(xs)) = xs для delta-encoding разом із varint, а varint окремо перевіряється на довільних невід'ємних числах, зокрема на межах 127/128 і 32-бітних значеннях. Індекс після save і load дає ті самі результати на випадкових запитах, а пошкоджений файл завершується контрольованою помилкою.

● **Fuzzy Search (після MVP).** Для випадкового рядка й відстані 2 результат пошуку збігається з повним перебором словника: містить усі терміни на відстані не більше 2 і жодного зайвого. Відстань Левенштейна симетрична, дорівнює нулю лише для однакових рядків і задовольняє нерівність трикутника.

### **Golden-тест для stemmer**

Офіційний тестовий набір Porter stemmer. Перевірка, що результат роботи системи не відрізняється від офіційної специфікації алгоритму.

Для цього беруться еталонні файли (вхідний словник (voc.txt) та очікуваний результат (output.txt)) безпосередньо з оригінального архіву автора алгоритму: [tartarus.org/martin/PorterStemmer/](http://tartarus.org/martin/PorterStemmer/). Тест автоматично проходить по кожному рядку вхідного словника і гарантує, що реалізація в системі посимвольно повертає той самий корінь, що і в офіційній реалізації.

### **Граничні випадки**

Явно виписані сценарії на межі коректної поведінки:

● порожній запит, запит лише зі стоп-слів: повідомлення користувачу, а не помилка;

● порожній документ, документ з одним словом: індексуються без помилок, довжина документа коректна ;

● глибоко вкладені дужки в запиті ((((cat)))): результат такий самий, як у cat;

● незбалансовані дужки та лапки, оператор без операнда (cat AND, NOT);

● термін, якого немає в індексі: порожній результат, не помилка;

● ~ на терміні, який є в індексі точно: нечіткий пошук не викликається, результат - лише точний збіг; (після MVP)

● ~ на терміні, якого немає ні в точному, ні в схожому вигляді: порожній результат, не помилка; (після MVP)

● phone~ AND number, де number відсутній у словнику: AND дає нуль документів незалежно від того, чи спрацював fuzzy для phone; (після MVP)

● пошук до виконання index: повідомлення про відсутність індексу;

### **Мутаційне тестування (Stryker)**

Тестування за допомогою Stryker оцінює якість тестів. Інструмент автоматично вносить у вихідний код невеликі зміни. Для кожної зміни запускається набір тестів. Якщо всі тести проходять, це означає прогалину в тестах: змінена поведінка залишилася непоміченою. Мутаційне тестування перевіряє, що тести справді реагують на зміну його поведінки. Мутації застосовуються до ядра системи: Query Parser, Query Executor, Scoring & Ranking і кодування delta/varint; шар CLI до мутаційного тестування не входить.

### **End-to-end тестування**

Наскрізні тести перевіряють роботу системи з точки зору кінцевого користувача, імітуючи введення команд у CLI-сесію (REPL) та перевіряючи стандартний вивід.

● **Базовий пошук**: Виконується команда index для фіксованої колекції, після чого stats і послідовність запитів з операторами AND, OR, NOT, дужками та фразами в лапках. Перевіряється, що stats показує коректну кількість документів і термінів, що кожен запит повертає очікувану множину документів, що запит у іншій формі слова (наприклад, у множині) дає той самий результат завдяки стемінгу, що фраза зі стоп-словом всередині враховує пропуск у позиціях і що позиції знайдених слів збігаються з номерами слів у файлі. Запит до терміна, якого немає в колекції, повертає порожній результат без помилки.

● **Стійкість інтерактивної сесії:** Імітація некоректних дій користувача в межах однієї сесії: синтаксично неправильні запити (search AND OR NOT), спроба завантажити неіснуючий файл, або виклик невідомої команди. Перевіряє, що процес не завершиться аварійно. REPL коректно перехоплює помилку, виводить зрозуміле текстове повідомлення користувачу і продовжує очікувати на введення наступної команди.

● **Життєвий цикл індексу та збереження стану (після MVP):** Виконується послідовність команд: index ./docs -> запис результатів stats -> збереження індексу save docs.bin -> "перезапуск" сесії (або примусове очищення індексу) -> завантаження load docs.bin. Перевіряється, що після завантаження команда stats повинна видати абсолютно ті ж показники (кількість документів, термінів), що й до збереження. Пошукові запити до завантаженого індексу повинні повертати ідентичні Top-K результати та BM25-оцінки, доводячи, що серіалізація/десеріалізація не втратила жодних даних позиційного індексу.

● **Складний інтеграційний запит (після MVP):** Введення запиту, який змушує працювати всі модулі рушія одночасно. Наприклад: search (people OR humann~) AND NOT "brown pillow". Перевіряється, що система успішно розбирає AST з дужками та фразою, застосовує стемінг та нечіткий пошук, знаходить точну послідовність слів для фрази, обчислює множини і виводить відсортований за BM25 список документів, коректно вказані позиції знайдених слів.

## **MVP**

В мінімально працюючій версії проєкту повинні бути реалізовані наступні модулі:

● Text Analyzer

● Inverted Index

● Query Parser

● Query Executor

● Scoring & Ranking

● SearchEngine

● CLI (частково: index, search, stats, help, exit)

**Сценарій використання MVP:** користувач запускає CLI, виконує index ./docs, потім у межах однієї сесії вводить довільну кількість запитів search <запит>, за потреби дивиться stats і виходить через exit. Для кожного результату CLI виводить ранг, source і BM25-оцінку, загальний час виконання й кількість знайдених документів, а також позиції знайдених слів у тексті (приклад: "people" - positions 12, 87, 140). Команда stats показує кількість документів та термінів.

**Тестування в MVP.** Для всіх модулів MVP реалізуються unit-тести та граничні випадки, для stemmer - golden-тест та два базові e2e (базовий пошук і стійкість сесії). Для Query Parser, Query Executor і Text Analyzer додається невеликий набір property-based тестів (fast-check) на базові властивості.

**Не входить до MVP (буде реалізовано на наступних етапах, але до моменту захисту):**

1. **Реалізація модулів Compression & Serialization та Fuzzy search:**

● **Збереження та завантаження індексу (save, load)** : це є додатковою можливістю над повністю працюючим пошуком. У MVP індекс існує лише в пам'яті поточної сесії й будується заново командою index.

● **Розмір індексу у stats.** Він з'являється разом із серіалізацією.

● **Нечіткий пошук (~):** він залежить від готових словника та виконавця запитів. У граматиці MVP символ ~ не підтримується, і запит із ним повертає повідомлення про помилку.

2.  **Повне property-based покриття, мутаційне та end-to-end тестування**
